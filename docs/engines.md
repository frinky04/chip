# Using Chip with any engine

Chip works with any game that can read glTF. Godot gets a ready-made addon; for every other engine (a custom one,
Unity, Unreal, a hobby engine) you supply two small pieces, and Chip does the rest:

```
your entity definitions ──generate──▶ entity manifest ──▶ Chip ──▶ level.glb ──▶ your loader
```

1. **A project file.** `chip.project.json` at the game's root tells Chip it's a game project, which engine it is, where
   the entity manifest lives and how its paths look. Chip finds it by walking up from the level and from the level's
   export path, like it finds `project.godot`.
2. **An entity manifest.** A JSON list of your entity classes and their typed properties. Generate it from wherever
   your game defines entities, so it can't drift from the code. Chip reloads it whenever it changes.
3. **A loader.** Your game reads the exported `.glb` with any glTF library and the `chip_*` keys in node extras:
   which nodes are entities (with their values), which collide, which are triggers.

```json
{ "version": 1, "engine": "Toy", "entities": "chip/entities.json", "assetPrefix": "assets/" }
```

Check the manifest with `Chip.exe --entities-check <game root>`, export headlessly with `Chip.exe --export level.chip`,
and load the result in the game.

Two more things a game can declare:

- **Surfaces.** These are tool materials of its own, under `"surfaces"` in the project file: a monster clip that blocks
  only monsters, water as a volume, a screen face the game swaps for a video. Each says whether it renders, collides
  or forms a volume, and how Chip draws it. The export marks every face with its surface (`chip_surface`).
- **Mesh classes.** These are entities made of level geometry (`"mesh": true` in the manifest): doors, platforms,
  screens with their own settings. Designers tie meshes to them, and the export puts those meshes under the entity.

## The sample game

[`samples/toy-game`](../samples/toy-game) is a complete example on a made-up engine, in about 400 lines of C#, that
never references Chip:

- `game/Entities.cs` declares five entity classes as C# classes with attributes, including `screen`, a mesh class.
- `game/Manifest.cs` generates `chip/entities.json` from them: `dotnet run --project game -- manifest`.
- `chip.project.json` adds two surfaces: `video` (the screen's face, drawn with a placeholder frame) and `monster_clip`.
- `game/Level.cs` loads an exported level: entities with their values and references, a mesh entity's geometry,
  colliders and volumes with their surfaces.
- `levels/demo.chip` is a level that uses every class: `Chip.exe --export levels/demo.chip`, then
  `dotnet run --project game -- play levels/demo.glb`.

`tests/Chip.Core.Tests/ToyGameTests.cs` runs that round trip on every test run, so the contract stays honest.

## Agents

`skills/chip` is an agent skill covering this whole workflow: connecting a game, changing entity classes, and editing
and exporting levels. To use it in a game's repository, copy the folder to `.claude/skills/chip` there (or wherever
that agent loads skills from).

## Godot

Godot needs no project file. The Chip import addon writes the manifest from your entity scenes and turns the export back
into scenes on import ([entities.md](entities.md), [the addon's README](../godot/addons/chip_import/README.md)). A
`chip.project.json` beside `project.godot` keeps Godot's conventions and overrides only the fields it sets, for example a
different manifest path.

## What changes per engine

| | Godot | Other engines |
|---|---|---|
| Entity manifest | written by the addon from `res://entities/` scenes | generated by your tools (or written by hand) |
| Loading the level | the addon, on import | your loader |
| Collider names | `-col`, `-colonly`, `-convcolonly` suffixes plus extras | extras only (`collisionSuffixes` turns suffixes on) |
| Material remap paths | `res://materials/brick.tres` | anything, written to `extras.chip_path` |
| Units | metres (export scale 1) | set the export scale (100 for centimetres) |

## Level properties and sky

A manifest class with `"world": true` declares per-level settings, edited under Level in the inspector
(Edit > Level properties clears the selection to reach it). Values save in `.chip` `world.properties` and export
in the glTF scene's `extras.chip_world`, beside `chip_flags`. World properties support asset kinds and `was` renames.
The built-in `sky` surface renders an unlit panorama, or a procedural overcast sky. Projects can set
`look.panorama` and `look.imageFrom` to preview a world asset property. See the
[manifest](../skills/chip/reference/manifest.md), [surfaces](../skills/chip/reference/surfaces.md) and
[export](../skills/chip/reference/export.md) references.
